# 테스트 컨벤션

이 문서는 테스트가 보호해야 할 범위와 최소 작성 규칙을 설명합니다. 테스트의 목적은 구현 라인 수를 채우는 것이 아니라 비즈니스 규칙과 bounded context 간 계약의 회귀를 방지하는 것입니다.

## 테스트 범위

| 종류 | 검증 대상 | 주요 도구 |
| --- | --- | --- |
| 단위 테스트 | 도메인 규칙, 애플리케이션 서비스의 호출 흐름, 어댑터 변환 | JUnit, Mockito |
| 슬라이스 테스트 | 컨트롤러 요청·응답, JPA 쿼리와 매핑 | `@WebMvcTest`, `@DataJpaTest` |
| 통합 테스트 | 여러 구성요소를 통과하는 이벤트·트랜잭션 흐름 | `@SpringBootTest` |

모든 계층에 같은 수의 테스트를 작성하지 않습니다. 변경으로 깨질 가능성과 실패했을 때의 영향을 기준으로 테스트 범위를 정합니다.

## Bounded Context 경계

- 각 bounded context의 내부 정책은 해당 영역의 테스트에서 검증합니다.
- 다른 영역의 정책을 추론하여 테스트를 작성하지 않습니다.
- 다른 영역을 호출하는 port와 adapter의 입출력 계약은 호출하는 영역에서도 검증합니다.
- 오래된 테스트의 의도를 확인할 수 없다면 현재 동작에 억지로 맞추지 않습니다.
- 현재 동작 자체를 보존해야 한다면 특성 보존 테스트라는 목적을 분명히 합니다.

예를 들어 Cart는 Course의 모든 내부 정책을 테스트하지 않습니다. Cart가 사용하는 가격, 판매 가능 여부, 강좌 스냅샷 계약과 변환만 검증합니다.

## 이름

### 클래스

- 일반 테스트는 `대상클래스Test`로 작성합니다.
- 여러 구성요소를 묶어 검증하는 테스트만 `기능명IntegrationTest`로 작성합니다.
- 기존 `*UnitTest`는 이름 통일만을 위해 일괄 변경하지 않습니다. 새로 작성하거나 수정하는 테스트부터 이 규칙을 적용합니다.

### 메서드

테스트 메서드는 `method_condition_expectedResult` 형식으로 작성합니다.

```java
void findById_existingUser_returnsInternalResult()
void findById_missingUser_returnsEmpty()
void addCartItem_unpurchasableCourse_throwsBusinessException()
```

`success`, `fail`만으로 조건을 생략하지 않고 메서드명에서 실행 조건과 기대 결과를 알 수 있게 합니다.

### DisplayName

`@DisplayName`은 호출자가 확인할 수 있는 결과를 나타내는 한국어 행위 문장으로 작성합니다.

```java
@DisplayName("존재하지 않는 사용자를 조회하면 빈 결과를 반환한다")
```

- `성공 -`, `실패 -` 접두사를 붙이지 않습니다.
- 문장 끝에 마침표를 붙이지 않습니다.
- 내부 구현 과정보다 호출자가 확인할 수 있는 결과를 표현합니다.

## 테스트 본문

Given/When/Then 순서로 작성합니다. 테스트가 짧고 구분이 명확하면 구역 주석은 생략할 수 있습니다.

- 하나의 테스트는 하나의 행위 또는 분기를 검증합니다.
- 긴 준비 코드가 반복되면 헬퍼 메서드나 테스트 데이터 생성 코드로 격리합니다.
- 코드로 알 수 있는 내용을 주석으로 반복하지 않습니다.
- 테스트 데이터에는 해당 시나리오에 필요한 값만 설정합니다.

## Mockito

새 테스트에서는 BDDMockito의 `given`과 `then`을 기본으로 사용합니다.

```java
given(repository.findById(id)).willReturn(Optional.of(entity));

then(repository).should().findById(id);
```

- 기본 1회 호출에는 `times(1)`을 쓰지 않습니다.
- 입력값이 계약의 일부라면 `any()`보다 정확한 값을 사용합니다.
- `any()`는 저장 객체를 캡처하는 경우처럼 정확한 값을 사전에 만들기 어려울 때 사용합니다.
- 발생하지 않아야 할 부작용은 `should(never())`로 검증합니다.
- 반환값이 없는 메서드의 기본 동작을 위해 `doNothing()`을 작성하지 않습니다.
- 사용하지 않는 스텁을 허용하려고 Mockito의 엄격성을 낮추지 않습니다.

## 결과 검증

- 성공 테스트는 반환 결과 또는 상태 변화를 검증합니다.
- 중요한 협력 객체의 호출과 실패 시 부작용 여부를 함께 검증합니다.
- `BusinessException`은 예외 타입뿐 아니라 오류 코드도 검증합니다.
- record나 값 객체는 가능하면 기대 객체 전체를 비교합니다.
- 결과 순서가 계약일 때만 `containsExactly`를 사용합니다.

```java
assertThatThrownBy(() -> service.execute(command))
        .isInstanceOf(BusinessException.class)
        .extracting("errorCode")
        .isEqualTo(ExpectedErrorCode);
```

## 테스트 중단과 삭제

다음 방식으로 테스트를 보관하지 않습니다.

- Java 파일 전체를 블록 주석으로 감싸기
- `@Test` 또는 `@ParameterizedTest` 메서드를 주석 처리하기
- 컴파일되지 않는 과거 테스트를 소스 트리에 남기기

`@Disabled`는 테스트가 현재 컴파일되고, 일시 중단 이유와 복구 조건 및 담당자를 명확히 기록할 수 있을 때만 사용합니다. 그 외의 오래된 테스트는 삭제하고 Git 이력에서 확인합니다.

## 테스트 환경

- ApplicationContext 테스트는 `test` 프로필을 사용합니다.
- 테스트 DB는 인메모리 H2를 사용하고 스키마는 테스트 실행 시 생성하고 제거합니다.
- 테스트 프로필에서는 Flyway를 실행하지 않습니다.
- 실제 S3, MinIO, 운영 DB 인증 정보를 사용하지 않습니다.
- 테스트용 외부 연동 설정은 가짜 값을 사용하며 로컬 셸 환경변수에 의존하지 않습니다.

## 실행과 완료 조건

일반적인 변경 후 전체 테스트를 실행합니다.

```bash
./gradlew test
```

테스트 파일을 삭제했거나 테스트 소스 구성이 바뀌었거나 이전 테스트 컴파일 산출물이 남았다고 의심되면 `clean` 후 전체 테스트를 실행합니다.

```bash
./gradlew clean test
```

개발 중 관련 테스트만 빠르게 실행할 수 있습니다.

```bash
./gradlew test --tests '*대상테스트명'
```

테스트 변경의 완료 조건은 다음과 같습니다.

- 관련 테스트와 전체 테스트가 통과합니다.
- 의도하지 않게 건너뛴 테스트가 없습니다.
- 테스트가 로컬 환경변수나 이전 컴파일 결과에 의존하지 않습니다.
- 변경과 무관한 테스트와 운영 코드를 형식 통일만을 위해 수정하지 않습니다.
